Anatomy of an agentic
design-system audit

Four agents, one designer, and a file that had been drawn rather than built. What automated — and what had to be decided by hand.

Scope: colour layer of the component library, 6,000-node sample.

00 · Where this came from

Two directions at once

A design file where the same red exists in four variants and half the colours are typed in by hand, bypassing the styles, is normal — not pathological. It's what any product looks like when it was made fast. The problem arrives the moment a team points an agent at that file: it won't ask which red is the right one. It will reproduce all four.

I came at this from two directions at once — working through Brad Frost's Subatomic methodology on design tokens, and learning how large language models actually work. Out of the collision came a question I couldn't put down: what does a design system need to look like for a machine to read it correctly?

For several years I'd been picking up products someone else had started, and I kept meeting the same file: drawn, not built. No components, no states, no scale. Before you can build a system on top of a file like that, someone has to go through the whole thing by hand — painstaking work, and rarely something anyone budgets for.

So the idea wasn't "let me try AI on something." It was: build agents that scan the design, surface everything that doesn't hold together, and — through a conversation with the designer — repair the file and construct the system. The conversation was in the design from the start: an agent can see an anomaly, but it can't know whether the anomaly was intended.

Part of that system I had built myself, from references. So the first thing the pipeline found was my own mistakes.

01 · The file

Drawn, not built

A crypto trading platform — one of the last projects I worked on. My job was to get the components in order and start building a design system. It made an ideal testbed: the system had to be built almost from scratch.

I decided to start with colour. It's the most visible, the most visibly broken, and the most verifiable: a colour has an exact value, and values can be counted.

The audit ran in two passes. First, inventory: the agent exported every variable, style and binding — everything the interface is actually painted with. Second, a usage scan: for each value it counted how that value is applied — as a text fill, as a shape fill, or as a stroke. This is what no linter shows you. A style's name doesn't tell you its role; the pattern of its usage does.

It walked the component library — 6,000 nodes. The output was a table of twelve findings, prioritised from critical to cosmetic. These were the most telling.

  • Three sources of white. A local style (724 uses), a twin from a remote library (839), and 74 hardcoded instances. All #FFFFFF. None connected.
  • Four near-identical reds. One had a style. The rest were eyedropper drift. Which one meant loss and which meant error was written down nowhere.
  • 431 hardcoded colours — 13% of all fills — including 122 copies of a red that already existed as a style.
  • Muted text at 2:1 contrast. Below WCAG minimums at any size. And it was the system's official grey.
  • A line-height bound to a blur radius. Two text styles had borrowed a variable called Scroll Edge Effect Blur Radius as their line-height. It worked — silently — because both values happened to equal 10.

None of this is an anomaly. A startup has a few months to make an MVP exist and a budget that goes toward what investors will see. The mess in the file isn't negligence. It's the price of speed, and it's a reasonable price.

The bill arrives later. When the product has grown, the team has doubled, and features cost more to produce than they should. And especially when the team starts generating interfaces with agents — and discovers the agent faithfully reproduces all four reds, because nothing in the file tells it which one is real. This case study is about that moment.

02 · Why agents

Not a plugin

Linters exist, and that's where you start. A linter will find 431 layers without a style. It will not tell you that the red hardcoded 122 times is the red that already has a style — while the one beside it should be deleted, not bound. It cannot derive a role from usage: that one translucent white was living two lives, 94 times as a surface and 106 times as a border, and therefore needed to become two different tokens.

No plugin answers a question that came into existence five minutes ago. The scan that counted usage by kind — text fill, shape fill, stroke — doesn't exist as a product. It was written for this file, in response to this question, in about a minute.

While this work was running, Figma shipped its own agent into open beta. Google Labs published DESIGN.md — a format for describing a design system to coding agents, built on the principle that tokens give an agent exact values while prose explains why those values exist. This work had arrived at the same principle independently. The value isn't in the format — it's in dragging a real, dirty file all the way through.

The mechanics are being commoditised, fast. What isn't: deciding what to run, how to read the result, and which decisions never go to a machine.

03 · The pipeline

Four agents, five human gates

A machine counts well and decides badly. So the work split into four steps: count first, then sort by meaning, then make the edits, then describe the result. The machine does the first step alone. On the rest it needs a human — in different places, for different reasons.

The places where the process stops and waits for a person, I call gates.

Agent one — inventoryExports everything the interface is painted with, and looks past style names to how they're actually applied: this colour used as text, this one as a fill, this one as a stroke. Names in a file often lie. Usage doesn't.
Agent two — classificationGroups duplicates, proposes what should become what, and compiles a list of questions it refuses to answer itself. Which of the four reds is the real one is not something it can decide.
Agent three — migrationRepaints only what matches exactly. Everything questionable goes into a separate queue, untouched.
Agent four — documentationAssembles the system's description from the same data the others worked on — which is why it doesn't drift from reality, unlike documentation written afterwards from memory.

Technically all of this ran through the Figma Plugin API: the agent connected to the file and could read and edit it — export styles, count usage, create variables, rebind nodes. Scripts were written for a specific question and run on the spot.

There were almost no variables in the file: a couple of stray ones, while the whole system rested on 23 colour styles. So the first thing the agent did after the inventory was build the variable structure from scratch — three collections (Global, Alias, Component) and the tokens inside them. Then it walked the component library and rebound every node from its old style to the new variable: 2,218 bindings in a single pass. All of it on a copy of the file. The original was never touched.

There turned out to be five gates. Four I designed in advance. The fifth appeared after the pipeline got it wrong.

04 · What broke

Zero errors, three times wrong

The pipeline preserved the colour and destroyed the transparency — badge backings that had been colour at 20% went flat, because the script replaced the whole paint object instead of one property of it.

It invented strokes that never existed, giving a green icon a red outline, because it had no concept that having no stroke is a state worth protecting.

It found exactly what it was asked about — reds, greens, ambers — and never mentioned an entire blue family doing systematic work in the file.

And the deepest one: while fixing colours, it walked every node inside instances — and each binding became an override. The instances stopped listening to their masters. In the name of centralising colour, the migration had quietly decentralised the component system. Automation produced exactly the disease a design system exists to cure.

An agent doesn't know what it doesn't know. None of these were errors inside its model of the world — the model simply had no concept of "transparency matters." Which makes the human's job less about checking answers than about checking the boundaries of the question.
05 · The architecture

Global → alias → component

Seven neutral values replaced twenty-three styles and a scatter of hardcodes. The platform is monochrome — lightness is the only axis of hierarchy — so the text tiers were re-spaced by contrast: 19:1 → 10:1 → 7:1.

The accessibility fix came from inside the file. The official muted grey failed WCAG at 2:1 — while a hardcoded grey someone had eyedropped 29 times passed AA at 7:1. The working design had already found the right value. The audit legalised it and retired the official one.

A value can arrive later. While I was working on the system, branding was running in parallel — the accent colour didn't exist yet. In the file, that pause cost twelve orphaned styles, half of them never used once. In a token architecture it costs one empty reference: the role exists, the value drops in the day the brand is ready, and everything referencing it updates by itself.

Independent validation. Every figure here came out of my own scripts — which is a fair thing for a sceptic to distrust. So the finished system was also written as a DESIGN.md and run through Google Labs' linter: zero structural errors across the three-tier architecture, every reference resolving. The tokens export cleanly to the W3C Design Tokens standard. It's the one number here I didn't award myself.

06 · What I'd change

Names first

  • Names firstI deferred renaming as cosmetic — values first, structure later. Wrong. In an agentic audit, names are input data. An agent reads a layer called text line and concludes it's a skeleton placeholder. It reads Frame 1000010369 and concludes nothing. Garbage names aren't merely useless — they're what an agent builds false hypotheses on.
  • A snapshot before, not an investigation afterBefore the first run, record the state of every node: colour, opacity, whether it has a stroke. Then comparing after migration takes a minute. I did it in the opposite order — migrated first, then worked out what had broken by staring at the screen.
  • Look at everything first, filter secondI asked for the reds and greens to be sorted out, and got reds and greens. An entire blue family stayed invisible because nobody asked about it.
  • Edits belong at master levelThe script walked every node, including those inside component instances — and every edit became an override. That's a design error, not an implementation one: I never asked which level of the hierarchy the change should live at.
  • Agree the naming convention with whoever reads itIf the system says surface-raised while the front end expects --color-bg-elevated, the tokens become one more dictionary to translate through — exactly the problem they were meant to remove.

What I wouldn't change is the human in the loop — and it was never a concession made after the agents disappointed me. What changed is the understanding of where the human stands. I thought: in the middle, between detection and repair. It turns out: at the entrance, asking whether the question is complete — and at the exit, asking whether the agent did only what it was meant to. The middle is the part that automates best.

Colour layer shipped. Typography, spacing and component naming: diagnosed, not yet rebuilt — four type families, three naming conventions, and spacing values divisible by nothing. Same process, next cycles.
