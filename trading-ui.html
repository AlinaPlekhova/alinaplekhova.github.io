00Case study

A design system for a crypto trading platform

A dense, dark-theme trading product had been designed screen by screen, with no system underneath. I audited it and built the foundations it was missing: a token architecture and a component library the team could maintain and extend.

01Context

A live product with no system underneath

The product is a crypto trading platform with a dark theme, dense data and dozens of surfaces: a trading terminal, analytics, payouts, evaluation flows.

The interface had been designed page by page. There was no shared layout, no component library and no single source of truth: every element was drawn directly on the screen it lived on. Colours drifted across several undertones, the same patterns were redrawn slightly differently each time, and every new screen meant making the same decisions again.

I started with an audit of what had shipped, then built the system underneath it, tokens first and components on top, while the product kept running.

02Tokens

A three-level token architecture

Raw values live once at the global level and are never consumed directly. A semantic layer maps them to roles. Component tokens exist only where a component needs its own override.

The trading group carries domain semantics for up and down, so the platform's meaning lives in the system rather than in one-off colour picks.

03Components

From tokens to the parts screens are made of

With the tokens in place, the next step was to turn everything that had been drawn by hand into reusable components.

Colour and icons came first, because every component depends on them. The greys were rebuilt on one cold undertone, so lightness carries the hierarchy in a mostly monochrome UI. Up/down and success/error are kept as separate roles even where they share a value, so trading and feedback can diverge later without a rename. The icon set was unified to one size and one default colour, recoloured through icon tokens rather than overrides.

On top of that I built the library: buttons, badges, selectors, message states, menus and headers, each with its full set of variants and states, so teams assemble screens from one source instead of redrawing them.

04Applied

Rebuilding real screens on the system

A system only proves itself when screens are built from it. I moved existing flows onto the new foundations, starting with the ones the team touched most.

Payouts is assembled from payout-level components: request states, the withdrawals table and popups, so every edge case is a variant rather than a separate drawing.

The hardest test is the trading terminal: chart, order book, order form and positions on one screen. Every colour, state and spacing there resolves through the same tokens, so density stays legible.

Below the chart sit five tables: positions, open orders, trade history, funding history and order history. They share one table structure, with empty states, dropdown actions and close-position popups as variants of it.

05Outcome

Where it got to

  • A token architecture of global, alias and component levels, with colour fully moved onto it.
  • A component library with variants and states spelled out, so screens are assembled rather than redrawn.
  • One documented source of truth the team can read and extend, where before there was none.

What's next

Colour is the foundation that's furthest along. Typography and spacing scales are next to come under the same structure, and connecting tokens through to engineering handoff is the direction I want to take it.
